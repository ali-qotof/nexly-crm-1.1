# تقرير PHASE 8 — Dashboard + Reports

## الحالة: ✅ مكتملة ومُختبرة (54/54 اختبار إجمالي)

## 1. ماذا تم بناؤه

- **`GET /api/v1/dashboard/manager`** (مدير فقط): كل مؤشرات القاعدة 8 — إجمالي/مخصص/غير مخصص
  للعملاء، عدد الموظفين، أوردرات اليوم/الأسبوع/الشهر، إجمالي المبيعات (بفلتر مدى تاريخ اختياري)،
  عملاء لم يُتواصل معهم إطلاقًا، متابعات مستحقة، عملاء يحتاجون إعادة محاولة. **كل استعلام
  Aggregated SQL (COUNT/SUM) — لا تحميل أي قائمة عملاء خام**، تحقيقًا الحرفي للقاعدة 8.
- **`GET /api/v1/dashboard/employee-performance`** (مدير فقط): صف لكل موظفة — عملاء مخصصون،
  تم التواصل/لم يتم، عدد الأوردرات، المبيعات، نسبة التحويل، متابعات معلّقة. **بدون Rankings أو
  Gamification** (القاعدة 30 صريحة بمنعها).
- **`GET /api/v1/dashboard/my-workspace`**: مساحة عمل الموظفة اليومية (القاعدة 29) — مبنية على
  بيانات فعلية فقط، لا تقديرية.

## 2. اصطلاح موثّق صراحة (وليس منطقًا مخفيًا)

"العملاء الذين يحتاجون إعادة محاولة" يُحتسب بمطابقة آخر تفاعل بكود حالة ثابت `retry_call`.
هذا الكود يُفترض أن يُنشئه المدير ضمن `status_configurations` لحالة "إعادة محاولة الاتصال"
(مذكورة حرفيًا في القاعدة 11). إذا اختار المدير كودًا مختلفًا، يجب تحديث الثابت في
`app/services/dashboard_service.py::RETRY_STATUS_CODE` — موثّق في تعليق أعلى الملف نفسه.

## 3. مشكلة اختبار حقيقية تم اكتشافها وإصلاحها (وليست خطأ في الخدمة)

الاختبار الأول لـ `test_manager_dashboard_counts_are_accurate` استخدم قيمًا مطلقة (`== 3`)
بينما قاعدة الاختبار مشتركة تراكميًا عبر كل الاختبارات في نفس التشغيلة (54 اختبارًا يُنشئون
عملاء/موظفين باستمرار). **الخدمة نفسها كانت صحيحة** — المشكلة في تصميم الاختبار. تم إصلاحه
بأخذ Snapshot قبل/بعد ومقارنة الفارق (delta)، بنفس الأسلوب المستخدم في اختبارات PHASE 3.
كما تم اكتشاف أن إنشاء المستخدم التجريبي قبل أخذ الـ Snapshot الأول كان يُسبب فارقًا صفريًا
لعدد الموظفين — تم تصحيح ترتيب العمليات.
